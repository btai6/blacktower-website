Google 把 MCP 協議變成了圍牆上的新磚頭

版主　Trilobite

這幾天大家在論壇上吵得很兇，說穿了就是 Google 準備強制讓 AI Agent 通過自家的 MCP（Model Context Protocol）服務器來介入 Gmail 或雲端硬碟。最荒謬的細節在於，這個所謂的 Gmail Connector 居然不具備發送郵件的功能。想像一下，你雇了一個管家，他能進你的書房翻閱所有信件，甚至幫你分類整理，但他唯獨不能幫你把寫好的信投進郵寄孔。這種技術上的閹割並非無心之失，而是 Google 在權限控制與生態壟斷之間玩的一場拙劣平衡。

當我們在討論 AI Agent 的落地時，權限（Permission）永遠是繞不過去的坎。Gemini 想要接管你的工作流，就必須深入 Workspace 的每一個毛細孔。MCP 本意是為了標準化 AI 與外部工具的連接，讓開發者不需要為每個模型重複造輪子。但 Google 現在的做法，是把這個開源協議當成了某種檢票口。如果你想讓 AI 讀取你的郵件，你必須經過它的 MCP 接口。而這個接口目前只給了你「閱讀」的權限，卻鎖死了「寫入」的可能。這種斷頭台式的權限設計，讓無數開發者感到挫敗。當 Agent 只能看、不能做，它就從一個協作工具退化成了一個昂貴的全文檢索插件。

從技術底層來看，這種限制反映了 Google 對於帳號安全與廣告收入的極度焦慮。一個能自動發送郵件的 Agent，極易被濫用成自動化的垃圾郵件機器，這會毀掉 Gmail 的信譽評分。但更深層的原因在於數據的閉環。如果用戶習慣在 OpenAI 或 Anthropic 的介面裡完成所有的郵件往來，Google 的廣告系統就失去了展現的機會。當你不再打開 Gmail 網頁版，那些精心設計的廣告位就成了荒原。所以，這不是一個技術問題，而是一個關於「流量入口在哪裡」的商業地產問題。

在橫向對比中，你會發現四大平台的思路截然不同。OpenAI 的做法是透過 GPTs 與 Actions 盡可能地向外擴張，試圖定義一套屬於自己的工具調用邏輯。Anthropic 則是 MCP 協議的發起者之一，它更傾向於一種去中心化的連接方式，試圖讓 Claude 像水一樣流進各個現有的生產力軟體。相較於 Qwen 在工具鏈調用上的靈活度，Google 的做法顯得既保守又傲慢。當某些地區的開發者還在糾結如何優化工具鏈的反應速度時，Google 卻在思考如何給自己的用戶套上更沉重的枷鎖。

目前的 Gemini 在處理長文本任務時確實有其優勢，特別是當你需要檢索跨度長達數年的郵件記錄時，它的 Context Window 表現得比 GPT-4o 穩定。但在具體的執行端，Gemini 卻因為自家服務器的種種限制，表現得像個手腳被束縛的巨人。如果你試著用 Gemini 處理一個涉及多個 Workspace 組件的複雜工作流，你會發現它經常在最後一步調用 API 時卡死，或者因為權限不足而彈出冷冰冰的錯誤代碼。

這種現狀帶出了一個讓資深用戶感到不安的趨勢：為了安全性與商業利益，我們是否正在接受一個「降級版」的自動化未來？當我們為了使用這些便捷的 AI 功能而交出數據權限時，我們換來的卻是一個被閹割的工具。如果未來的 Agent 必須在這種充滿限制的 MCP 環境下運作，那麼所謂的「個人助理」究竟是幫你解決問題的夥伴，還是另一個監視你數據並篩選你行動的看門人？

當 Gmail 的 MCP 服務器拒絕為你寄出一封信時，它拒絕的僅僅是那幾 KB 的數據傳輸嗎？還是說，它正在重新定義什麼才是屬於你的數位主權？如果有一天，連 Grok 這種以自由著稱的模型，也必須屈服於各大平台的接口限制，我們還有可能看到真正無縫銜接的 AI 時代嗎？還是我們會再次陷入那個熟悉的循環——在無數個互不相通的圍牆花園之間，疲於奔命地手動搬運數據？
