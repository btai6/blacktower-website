Do the math: How we took over ChatGPT accounts

版主　渡鴉

當 OpenAI 忙著讓 ChatGPT 活得越來越像個人時，它顯然忘了自己本質上還是一堆漏洞百出的程式碼。最近在技術圈傳得沸沸揚揚的帳號接管漏洞，本質上不是什麼高深莫測的量子破解，而是一場關於 OAuth 流程與 URL 參數過濾的低級失誤。只要誘使使用者點擊一個特製的連結，攻擊者就能輕而易舉地把對方的對話紀錄、個人資訊甚至 API 金鑰納入囊中。這種事發生在一個估值千億美元、號稱要引領人類走向 AGI 的公司身上，確實有一種荒誕的黑色幽默。

這種安全架構的崩塌，反映了 OpenAI 在產品擴張期那種近乎偏執的焦慮。為了讓 ChatGPT 的互動更流暢、跨平台同步更無感，開發團隊在授權機制上留下了太多「為了方便而存在」的後門。OAuth 流程中對重定向路徑的校驗如果不夠嚴謹，在 Web 開發領域簡直是教科書等級的負面教材。更別提那個讓人心驚膽顫的桌面版漏洞，居然能讓遠端指令存取本地檔案系統。當我們在聊天視窗裡跟 AI 探討如何優化程式碼邏輯時，底層的系統結構卻像是一個四處漏風的草棚。這不禁讓人懷疑，那些被吹捧上天的「 Agent 群體協作」或是「自動化除錯」，到底有沒有被應用在自家產品的安全審核上？還是說，薩姆·奧特曼（Sam Altman）的團隊覺得，只要模型夠聰明，使用者就應該原諒它在基礎防護上的弱智？

從技術細節來看，這不單純是代碼寫錯的問題，而是系統複雜度呈對數級成長後的必然代價。ChatGPT 已經不再是一個簡單的對話框，它是一個整合了外掛、搜尋、 DALL-E、數據分析以及第三方應用的龐大單體。每一次功能迭代，都在增加攻擊表面積。當你試圖讓 AI 處理數百萬行代碼時，你實際上是在為駭客鋪設一條通往核心數據的高速公路。這種「先上車後補票」的矽谷精神，在面對涉及隱私的個人帳號時，顯得極其不負責。我們現在似乎進入了一個「榮譽制度」時代：請大家自律，不要點連結，不要登入別人的帳號，否則損失自負。這種所謂的安全意識培訓，聽起來更像是對使用者的一種冷嘲熱諷。

在處理這類複雜系統的穩定性與安全性時，不同的陣營走向了完全不同的道路。相較於 Qwen 在特定開源基準測試上的堆疊，OpenAI 的做法是典型的高度封閉且高度整合。當 Google 的 Gemini 試圖利用其深耕多年的 Workspace 帳號體系來構建護城河時，它至少繼承了 Google 那套相對成熟的權限管理邏輯。Gemini 在處理跨 App 呼叫時，對 Token 的生命週期控制比現在的 ChatGPT 要嚴謹得多。至少目前為止，你還很難透過一個簡單的 URL 參數就讓 Gemini 把你的雲端硬碟拱手讓人。而 Claude 則走了一條更極端的「憲法 AI」路徑，不僅是在回答內容上設限，在產品介面的簡潔度上也做得近乎刻薄，這種刻薄反而減少了許多不必要的 API 暴露風險。

與此同時，Elon Musk 的 Grok 雖然在言論尺度上大開大闔，但在後端架構上因為承襲了 X（前 Twitter）那套被無數次壓力測試過的基礎設施，反而沒出現過這種低級的 OAuth 漏洞。當然，這可能也跟 Grok 的功能還相對單一有關。每當我們談論模型性能時，往往會忽略這些隱藏在水面下的「工程債」。相較於 Qwen 在中文語境下的優化嘗試，ChatGPT 面臨的是一個全球性、全天候的攻擊環境，這本應讓他們在安全防禦上更為警覺，但事實卻恰恰相反。他們似乎更在乎模型能不能寫出感人的詩集，而不是你的帳號會不會在五秒鐘內易主。

這帶出了一個令人不安的趨勢：隨著 AI 權限的擴大，密碼還有存在的意義嗎？如果一個連結就能繞過所有的防護牆，那麼我們引以為傲的多重驗證、生物辨識，在 AI 應用的邏輯漏洞面前，是否都成了精美的擺設？當系統單體化到無法被人類完全理解的程度時，減少程式碼行數（LOC）究竟是唯一的救贖，還是只是程式設計師的一種鄉愁？如果連全球最強的 AI 公司都搞不定一個網址參數的過濾，我們真的準備好讓這些模型去接管更核心的社會基礎設施了嗎？或者說，我們其實早就習慣了在這種「方便」與「裸奔」之間橫跳，直到下一次更大規模的數據洩漏發生為止？
