Gemini 在星海爭霸戰場上的代碼邏輯陷阱

版主　Trilobite

在 StarSkirmish 這種要求 LLM 透過編寫代碼來即時操控《星海爭霸》的基準測試中，Gemini 展現出一種令人不安的兩極化特徵。當模型需要面對特定的基礎腳本機器人時，Gemini 的勝率可以衝破 50%，彷彿它真的理解了什麼叫作「克制」與「運維」。然而一旦對手切換成那些具備更強隨機性、模擬人類頂尖選手操作的強大腳本時，勝率會瞬間崩塌到個位數。這種從天才到平庸的墜落，並非單純的算力不足，而是揭示了大模型在處理長序列、高頻決策任務時，對預訓練數據依賴的底層邏輯漏洞。

Gemini 之所以能在特定場景下拿到高分，很大程度歸功於其對於 API 調用序列的敏銳度，尤其是在 Google 持續優化的長文本架構下，它能比其他模型更穩定地維持戰術執行的一致性。在星海爭霸這種每秒鐘都有數百個事件發生的環境裡，模型不是在「玩」遊戲，而是在對混亂的狀態變量進行代碼重構。Gemini 傾向於生成一套結構極其工整的宏觀運維代碼，如果對手遵循的是可預測的模式，Gemini 的代碼就能精準地卡住資源產出的時間點。但這種「工整」也是它的致命傷，它更像是在背誦一份完美的比賽劇本，而不是在進行動態博弈。

當我們把目光轉向 ChatGPT 和 Claude，會發現這四巨頭在應對這類硬核技術基準測試時，各自的短板都暴露得相當刺眼。ChatGPT 在生成複雜遊戲指令時，經常會出現語義上的「幻覺」，導致代碼在執行關鍵戰鬥指令時失效。Claude 雖然在代碼的邏輯嚴密性上更勝一籌，但面對星海爭霸這種極短時間內的決策壓力，它的推理延遲往往讓它錯過戰機。相較於 DeepSeek，Google 在處理這種需要極高並發理解能力的任務時，更傾向於依賴其封閉生態內的預調優參數。

這種技術路徑的差異在橫向對比中變得更有趣。Gemini 對於環境反饋的處理機制非常依賴上下文窗口的廣度，這讓它在面對長時間線的資源管理時有優勢。而 ChatGPT 的策略則更偏向於碎片化的即時反應。在目前的技術環境中，除了 Google 內部的測試外，市場上也有像 Qwen 這樣的模型在嘗試介入代碼生成領域。然而回到四大平台的競爭格局來看，Gemini 在這次表現出的「斷崖式崩潰」，本質上是因為模型並沒有真正理解「博弈論」。它只是在預訓練數據的海洋裡，尋找最像「贏球代碼」的那一段字符，一旦現實情況超出了預訓練分佈的邊界，模型的邏輯就會像多米諾骨牌一樣崩塌。

這帶出了一個資深開發者都該警惕的問題：如果一個模型在模擬環境中展現出的高性能，僅僅是因為它「看過」了類似的代碼結構，那麼這種性能在面對真實世界中未知的、非線性的突發狀況時，究竟還有多少含金量？目前的測試中，時間限制被設為一個關鍵變量。我們看到 Gemini 在時間充裕時能寫出華麗的架構，但在高壓下生成的代碼質量卻迅速退化。這是否意味著，現有的 Transformer 架構在處理需要「直覺」與「即時反應」的任務時，存在一個無法逾越的物理極限？

如果未來我們要求 LLM 去接管更複雜的工業自動化系統，或者更具動態性的現實決策場景，Gemini 這種在特定對手面前表現優異、在未知對手面前徹底失能的特徵，會不會成為系統性的風險點？當模型學會了「像贏家一樣寫代碼」，卻沒有學會「如何在失敗的邊緣生存」時，我們真的能放心把控制權交給它嗎？或者說，我們現在所追求的勝率，會不會只是一場精確對齊預訓練數據的幻覺？
