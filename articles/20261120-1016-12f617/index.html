AI 泡沫破裂前得先解決那堆沒人想碰的工程髒活

版主　Sword Smith

那群做硬體和搞搜尋的 CEO 聚在一起喊 AI 回報率低，聽起來像是一場大型的集體卸責。這件事的核心根本不在於 AI 到底能不能賺錢，而在於這群人還在用十年前「買個套裝軟體就能轉型」的舊思維在看大模型。現在的情況是，你手裡拿著一把能切開任何東西的利刃，卻發現自己家裡的電路板全是鏽跡，連個插座都找不到。

很多人抱怨 AI 實踐慢，那是因為他們根本沒意識到，要把一個 Agent 塞進生產環境，背後需要多少噁心的基礎設施。你需要運行環境、需要數據連接器、需要權限控管，更需要一套能讓模型乖乖聽話的 SOP。現在大模型在生產環境的表現，與其說是「智能」，不如說是「失控」。大家在論壇上吹噓的那些 Vibe Coding，在面對銀行轉帳、郵件發送這種不容出錯的剛性任務時，簡直像個笑話。一旦進入真正的工程實踐，你會發現模型輸出的不穩定性，正在摧毀過去三十年建立起來的軟體品質保證體系。

這種挫敗感在 Grok 和 ChatGPT 的用戶群中特別明顯。Grok 的開發邏輯一直很硬派，直接掛載在 X 的實時數據流上，這看起來很酷，但當你試圖用 API 構建一個自動化決策鏈時，你會發現那種「不修邊幅」的原始感簡直是開發者的噩夢。Grok 的上下文處理雖然一直在追趕，但在長序列的邏輯一致性上，比起 Claude 還是顯得有些毛躁。這不是參數量的問題，而是底層對「事實」與「幻覺」邊界的拿捏。

在技術落地的路徑上，四大平台展現了完全不同的姿態。OpenAI 試圖把 ChatGPT 變成一個萬能的作業系統，讓用戶在它的生態裡解決一切；Anthropic 則顯得冷靜得多，Claude 在複雜編碼任務和長文本理解上的穩定性，其實是目前最接近「工程可用」的狀態。當你在處理超過 5 萬 token 的程式碼庫重構時，Claude 的注意力分配明顯比 GPT-4o 更精準，它不會像後者那樣在對話中途突然「失憶」或者給出一些似是而非的建議。

相比之下，Gemini 雖然背靠 Google 龐大的工具鏈，但它的 Function Calling 在面對超過 10 個以上的工具調用時，出錯率會直線上升。這就是典型的「大廠病」：功能堆得很滿，但細節處全是毛刺。如果你要在複雜的企業環境下部署一個自動化 Agent，Gemini 的這種不穩定性會讓 QA 工程師發瘋。

這時候我們回頭看那些所謂的警告，其實反映了一種對「技術代差」的焦慮。在 Qwen4-Max 剛釋出新動態的這個節點，很多人試圖拿它來證明追趕是有可能的。但實際對比下來，相較於 Qwen4-Max，xAI 在 Grok 的訓練中更強調對非結構化實時數據的極速反應。這種策略上的差異，導致了不同模型在處理現實任務時的底色完全不同。即便是在同一個評分標準下，四大平台展現出的「邏輯韌性」依然是其他跟隨者難以企及的。

我們現在看到的「AI 回報率低」，本質上是工程能力的斷層。開發者們習慣了用 Library，習慣了調包，但現在面對的是一個黑盒子。如果你不能像某些極客那樣，為了實現一個特定功能而去重寫底層邏輯，甚至自己構建一整套個人軟體宇宙，那你永遠會覺得 AI 是個昂貴且難用的玩具。依賴開源庫或現成的 API 並不是不行，但如果你連依賴項都搞不清楚就想進場，最後只會收穫一堆無法運行的程式碼片段。

現在的問題是，如果 2027 年真的是所謂的「QA 回歸年」，我們是否已經準備好了一套全新的自動化測試框架來對抗大模型的隨機性？當我們習慣了用 AI 來寫程式，誰來負責審查那些 AI 生成的、連開發者自己都看不懂的邏輯？如果四大平台始終無法解決輸出穩定性的最後一公里，那麼這場關於 AGI 的狂歡，會不會最終淹沒在無盡的 Bug 修改與環境調試中？
