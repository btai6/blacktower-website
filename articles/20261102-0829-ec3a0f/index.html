Backdoor in Claude Code for VS Code extension on t

版主　Scholar

當開發者還在為 Claude Code 帶來的自動化修補感到驚艷時，一場發生在 Cursor Marketplace 的後門風暴正悄悄收割開發環境的權限。這場意外與其說是技術失誤，不如說是對開發者心理防線的一次精確打擊。當人們習慣了在 IDE 中點擊「Install」來換取生產力提升，卻很少有人意識到，那個被命名為 Anthropic 官方擴展插件的背後，可能藏著通往你本地源碼庫甚至伺服器終端的鑰匙。這並非科幻小說，而是已經發生的現實：一個偽裝成官方工具的惡意擴展，在被下架前已經完成了對特定開發群體的精準滲透。

這次事件的核心在於「信任鏈」的斷裂。在 VS Code 或 Cursor 這種高度依賴插件生態的環境中，開發者對特定大模型品牌的忠誠度往往轉化為盲目的下載行為。當有人在 Cursor Marketplace 上傳了一個名字極具誤導性的 Claude Code 擴展時，大多數人甚至不會去校驗發布者的數位簽章。這種行為邏輯與當年針對開源代碼倉庫的 Typosquatting 攻擊如出一轍，只是這次的誘餌從熱門 npm 包換成了當紅的 AI 代理工具。對於那些在工作流中深度依賴 Claude 的開發者來說，這種安全漏洞簡直是懸在頸後的達摩克利斯之劍。

從技術層面看，這類惡意擴展的威脅遠超傳統惡意軟體。因為 AI 擴展通常需要極高的權限來讀取文件系統、執行終端命令，甚至調用系統級 API。如果說 ChatGPT 的 Web 端尚且被困在沙盒裡，那麼整合進 IDE 的 Claude 或 Grok 則像是獲得了管家鑰匙的訪客。當惡意代碼被注入到 extension 的啟動腳本中，它能輕易地攔截你的 API Key，或者在後台悄無聲息地將你的核心代碼庫上傳到遠端伺服器。這種攻擊方式利用了開發者對「AI 賦能」的急切渴望，將安全審查的優先級降到了最低。

我們對比一下目前四大平台的生態策略。ChatGPT 傾向於將一切控制在自己的桌面應用或 Web 端內，這種閉環雖然限制了靈活性，卻也築起了一道防禦牆。Gemini 則是背靠 Google 強大的 Workspace 安全體系，其插件權限分發極為克制。相較於 Qwen3.8-27B 在某些特定任務上的活躍表現，Claude 在開發者社群中擁有的極高滲透率，使其成為了駭客眼中的一塊肥肉。在同樣的技術環境下，Qwen3.8-27B 被社群討論的重點往往在於模型權重的分發，而 Claude 則因其強大的代碼推理能力，被迫捲入了更複雜的插件生態博弈中。

問題在於，即便受污染的擴展版本已經從商店移除，那些已經被「感染」的開發環境該如何清理？這不是簡單的刪除插件就能解決的問題。如果惡意腳本已經在本地執行過，它可能已經在你的 shell 配置文件中留下了後門，或者在你的環境變量裡安插了監聽器。這種隱蔽性極強的持久化攻擊，讓原本追求效率的 AI 工具變成了企業安全團隊的噩夢。當我們在談論 AI 安全時，總是在討論對齊、討論幻覺、討論 Prompt 注入，卻忘了最基礎的軟體供應鏈安全依然是那塊最短的木板。

這種「官方感」的幻覺正在消磨開發者的警覺性。一個掛著 Anthropic 頭像、描述寫得天花亂墜的插件，就能騙過上萬名資深工程師，這本身就是對現代開發文化的一種諷刺。我們是否過度信任了這些第三方 Marketplace 的審核機制？或者說，當 AI 模型本身已經進化到能寫出完美代碼的程度時，我們是否也默認了這些圍繞模型構建的工具鏈同樣無懈可擊？

如果下一次，這類惡意代碼不是由偽裝者上傳，而是直接由某個被污染的模型權重生成的呢？當 AI 在為你修復 Bug 的同時，順手在你的登錄邏輯中留下一行不易察覺的後門，你是否還有能力在成千上萬行的代碼審查中揪出那個幽靈？我們追求的自動化開發，究竟是通往效率的捷徑，還是主動向未知的風險敞開了大門？或許在未來，區分一個工具是助手還是間諜，將成為比寫出一段高效算法更難的課題。
