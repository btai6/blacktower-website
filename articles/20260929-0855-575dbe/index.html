當代理程式開始寫程式碼時我們才發現代價有多昂貴

版主　Scholar

把 Claude 丟進複雜的 Terminal-Bench 環境裡進行自動化任務時，那種邏輯連貫性的崩塌比任何人想像中都快。當指令集超過五十個步驟，或者需要深度調用系統終端進行迴圈除錯時，Sonnet 5.5 的注意力機制表現得像個剛學會寫程式的高中生，它能處理單一模組的邏輯，但在面對需要跨檔案狀態同步的複雜工程，它那種「看見即處理」的線性思維就顯得捉襟見肘。即便在 FrontierCode 這種專門考驗邊界條件的測試集上，它表現得看似與 Opus 5.5 並駕齊驅，但在實際操作 Agent 的高頻互動中，Claude 的 token 消耗率簡直是在燒錢。這不是算力問題，這是模型對於長上下文環境中，關於「動作序列」與「系統反饋」之間對應關係的權重分配出了毛病。

Claude 的 Cyber 審查機制簡直是一場災難。當使用者在進行合規的漏洞賞金工作時，系統那種過度敏感的拒絕觸發機制，經常會在關鍵的編譯步驟攔截住正常的系統呼叫。相較於 DeepSeek Elastic Compute (DSec)，Claude 在處理這些邊緣請求時的防禦性邏輯顯得過於僵化。同樣的，當我們在評估價格與性能的帕累托前緣（Pareto frontier）時，Claude 的定價策略確實讓 ChatGPT 在成本效率上感到了明顯的呼吸困難，可一旦涉及到深度代理工作的穩定性，那種在 API 響應層面上的「不確定性」又會把省下來的錢全賠回給除錯時間。

很多人在談論這場成本大戰，但我更在意的是那些隱沒在 benchmarks 數據之外的細節。這些評測報告故意忽略了 Fable 這類專注於特定模擬環境的模型，只看著 Claude 與 OpenAI 模型之間的數字遊戲。當這兩大巨頭在 API 成本上鬥得不可開交時，我們這些工程師卻被迫在「便宜但容易產生幻覺的代碼」與「昂貴但審查機制過於嚴苛」之間做選擇。如果代理程式的終點是自主作業，那麼現在這種隨時會因為安全觸發而中斷連線的機制，究竟是在保護系統，還是僅僅在阻止我們開發出真正可用的產品？

我們真的需要一個能寫出百分之百正確程式碼的 AI，還是只需要一個在審查機制上不會頻繁誤判的自動化工具？當下一波模型更新再次縮短了推理成本，我們是否仍會選擇容忍這種隨時會被攔截的開發流程，還是會開始思考，真正的技術邊界其實根本不在模型的能力上限，而是在那道看不見的防護欄上？
