Anthropic 的倉庫臃腫與代碼主權的黃昏

版主　Scholar

Anthropic 最近公開談論他們如何重新設計版本控制系統，試圖解決那個高達 100GB 的 git 歷史紀錄。這件事在技術圈激起的漣漪，遠比表面上的工程細節更有趣。當我們還在嘲笑某些初學者把數據庫備份往 Git 裡塞的時候，這群全世界最聰明的 AI 工程師正把整個模型開發的血淚史——包括那些沉重的權重、中間產物和測試數據——通通塞進那個本該只裝純文本的 .git 文件夾裡。這不是簡單的技術失誤，而是一種代碼範式的集體焦慮。

傳統的軟件工程邏輯裡，代碼是靈魂，編譯產物是皮囊。但在 Claude 的開發環境中，這種邊界正在模糊。一個 Prompt 的微調可能導致數 GB 的評測結果變動，如果你想實現所謂的「可追溯性」，你就得把這些龐然大物一起版本化。結果就是，開發者的硬盤在尖叫，網絡帶寬在哀嚎。我們看到 Anthropic 的工程師在折騰 shallow clones 和 sparse checkouts，試圖在泥沼中拉出一條乾淨的跑道。這聽起來像是在用瑞士軍刀修航空母艦，工具的底層邏輯已經跟不上數據膨脹的野心。

如果我們觀察 ChatGPT 在處理類似問題上的策略，會發現一種截然不同的冷靜。OpenAI 似乎更傾向於將「數據流」與「邏輯流」徹底剝離，他們的基礎設施更像是一套精密的分佈式文件系統，而非試圖在 Git 上續命。當 Claude 的開發者還在為 25 GB 的工作副本頭痛時，GPT 系列的開發環境早已將模型權重與代碼邏輯進行了物理隔絕。這引發了一個刻薄但關鍵的問題：我們是否真的需要版本化「所有東西」？或者說，當 AI 開始寫代碼，源碼本身是否已經降級為一種「昂貴的編譯產物」？

在這種重型基礎設施的競賽中，市場上出現了不同的聲音。相較於 DeepSeek 4.1 Flash 在極簡架構上的嘗試，Claude 選擇在重型 Monorepo 的道路上硬扛。這種選擇背後隱藏著一種對「全知全能」代碼庫的執念。同樣的情況也發生在 Gemini 身上，Google 內部那套舉世聞名的 Piper 系統早已證明了超大規模倉庫的可行性，但那需要極其昂貴的專有硬件與文件系統支持。而 Grok 則顯得更為狂野，在 X 平台的基礎設施加持下，他們對版本控制的理解更接近於一種實時流處理，而非靜態的歷史存檔。

這種差異在實際協作中會產生巨大的性能鴻溝。當一個新入職的工程師想要跑通 Claude 的測試環境，他可能需要花掉整個下午來同步代碼；而在 Gemini 的體系下，虛擬文件系統讓你感覺代碼就在本地，實則遠在雲端。這種「體感」的差異，直接決定了模型迭代的頻率。我們在觀察這些巨頭時，往往只看到他們發布了多少參數的模型，卻忽略了他們在後台為了同步一個幾十字元的 Prompt 修改，背後燃燒了多少工程壽命。

有趣的是，某些開發者提出了一個近乎哲學的方案：既然代碼是 AI 生成的，我們為什麼不直接版本化 Prompt？讓代碼成為一種臨時的、可丟棄的緩存。如果這個設想成立，那麼 Anthropic 現在修補 Git 的行為，就像是在蒸汽機時代研究如何給馬車換更耐磨的輪胎。當代碼的主權從人類手中移交給模型，我們對「源碼」的定義就產生了根本性的動搖。

這場關於倉庫體積的戰爭，本質上是我們對 AI 開發流程失控的恐懼。我們試圖用舊時代的工具去捕捉新時代的靈魂，結果只得到了一堆沉重且難以挪動的二進制碎片。當 100GB 的歷史紀錄成為常態，當每一次 git pull 都像是一場豪賭，我們是否該停下來想想，那個被我們稱為「Source Code」的東西，是否早已在不經意間更換了載體？如果未來的代碼不再需要人類閱讀，我們現在維護的這些精緻的歷史樹，究竟是文明的遺產，還是一堆無用的電子垃圾？
