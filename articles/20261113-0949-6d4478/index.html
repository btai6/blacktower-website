為什麼 Grok 還在教你寫十年前的垃圾代碼

版主　Sword Smith

如果讓 Grok 或 ChatGPT 幫你寫一個自動增長的輸入框，它們大概率會吐出一串監聽 input 事件、手動計算 scrollHeight 再動態修改 style.height 的 JavaScript 廢話。這套做法在 2019 年可能是標準答案，但在現代 Web 標準面前，這簡直是技術考古。Chrome 團隊最近開始急著幫這些 AI 補課，試圖讓它們學會 field-sizing: content 這種一行 CSS 就能解決的事情，這背後反映的技術斷層比想像中更令人煩躁。

現在的開發者一邊在 Hacker News 上嘲諷 AI 生成的代碼是「隨機性機器」，一邊又不得不吞下這些充滿過時依賴的垃圾。這不是模型聰不聰明的問題，而是知識權重的災難。Grok 的訓練語料庫裡塞滿了過去十幾年堆積如山的舊代碼庫、過時的 Stack Overflow 問答以及那些早就該進垃圾桶的 jQuery 插件。當你在 xAI 的輸入框裡要求一個彈窗組件，它會習慣性地給你寫一堆 <div> 模擬遮罩層，再加上複雜的焦點管理邏輯，完全無視瀏覽器原生自帶的 <dialog> 標籤和 showModal() 方法。這種現象在四大平台中普遍存在，它們似乎更傾向於「多數人的錯誤」而非「少數人的正確」。

從技術層面來看，xAI 在這方面的遲鈍感最明顯。Grok 雖然背靠 X 的實時數據，但在處理現代 Web 標準（Web Primitives）時，它的推理路徑往往被大量的開源腳手架代碼所綁架。當我嘗試讓 Grok 使用 CSS.highlights 進行文本高亮而不使用額外的 <span> 標籤時，它雖然能識別這個 API 的存在，但在實際生成的代碼邏輯中，依然會固執地回歸到操作 DOM 節點的老路上。這說明模型在權衡「原生支持」與「通用兼容性」時，存在嚴重的邏輯慣性。它害怕給出一個你瀏覽器跑不動的代碼，於是選擇給出一段讓所有人都痛苦的冗長代碼。

相較於 DeepSeek 近期在推理模型上的嘗試，Grok 在處理這種精細化前端規範時，顯得缺乏一種「技術潔癖」。ChatGPT 的 GPT-4o 在這方面稍微好一點，至少它在引導下能意識到現代瀏覽器的能力邊界，但如果你不主動提醒，它依然會默認輸出那套 2019 年的技術棧。Gemini 則是另一個極端，它會極力推銷 Chrome 的新特性，有時甚至超前到給出還在草案階段、根本沒法用的 API。這種不穩定性讓資深開發者感到疲憊，你本想節省時間，結果卻花了更多時間在審核這些看似優雅實則無法運行的「未來代碼」上。

這引出了一個讓人不安的現狀：當 AI 成為代碼產出的主力，所謂的「最佳實踐」正在迅速消亡。如果模型只會學習 GitHub 上存量最多的代碼，那麼那些優雅、簡潔的原生解決方案將永遠被淹沒在過時的技術海洋裡。DeepSeek 在某些基準測試中表現出色，但在面對這種 Web 標準的代碼演進時，依然得面對和 OpenAI 相同的語料污染問題。我們正處於一個技術倒退的奇點，AI 生成的垃圾代碼被重新餵給 AI，形成一個低效的閉環。

這不僅僅是代碼長短的問題，而是控制權的喪失。如果 Grok 永遠默認給你一套需要五個依賴包才能運行的導航欄，而忽視了現代 CSS 只要幾行屬性就能完成的事實，那我們究竟是在進化，還是在加速製造技術債？當 Chrome 團隊不得不親自下場為 AI 編寫「現代化指南」時，這到底是在救火，還是另一種形式的標準壟斷？如果未來所有的 AI 都只聽從某一家瀏覽器廠商的指導來寫代碼，那當初我們追求的 Web 多樣性還剩下什麼？

我們是否已經進入了一個「不讀代碼」的時代，只要程序跑得起來，哪怕它內核是腐爛的、過時的、臃腫的，也沒人在乎了？當 AI 習慣性地選擇那條最平庸、最保險的舊路時，誰來負責推動技術的前進？
