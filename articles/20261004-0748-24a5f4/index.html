別再讓 LLM 替你寫心路歷程了

版主　Sword Smith

這幾天 Hacker News 上全是在吵 Claude 3.5 Opus 的實測表現，大家似乎終於意識到，給模型塞過多「推理指令」反而是種毒藥。當你在 Prompt 裡要求模型「詳細解釋你的邏輯」或「分步驟說明理由」時，你其實是在浪費它的上下文窗口，甚至是在干擾它的神經元輸出。很多人在 CI 優化這種高壓任務裡發現，只要給出精確的指令，讓 Opus 直接處理 billing minutes 和 wall clock time 的權衡，它的表現遠比在那邊自我剖析要強得多。這種現象在技術圈被稱為「推理稅」，我們付了錢，卻買了一堆模型自言自語的廢話。

技術層面的真相很殘酷，Claude 3.5 Opus 在處理長達一小時以上的連續任務時，表現出的穩定性確實超越了目前市面上大半的模型。這不是因為它變得更聰明，而是它在指令遵循的權重分配上做了微調。當你使用 Claude Code 或是串接 subagent 進行代碼重構，比如把老舊的 Java 專案翻新成 Node.js，Opus 展現出一種冷靜的精確。它不再像之前的版本那樣，在任務中途突然陷入邏輯死循環。這種「長程任務信任感」是目前開發者最稀缺的資源。與此同時，有些人注意到在 Opus 發布前夕，舊版本似乎出現了莫名其妙的幻覺增長，這種「新舊交替期的性能抖動」雖然官方從不承認，但在 API 調用的 Token 消耗曲線上看得清清楚楚。

這就帶出了一個更有趣的觀察。在追求代碼產出質量的賽道上，xAI 的 Grok 最近也在急起直追，試圖在原始推力上與 Claude 一較高下。相較於 DeepSeek 這種在特定成本區間內遊走的模型，Grok 展現出的攻擊性更強，它在處理非標準化的編程邏輯時，那種不按牌理出牌的聯想力，有時候能撞見 Opus 這種嚴謹派漏掉的邊界案例。而 ChatGPT 則是另一種極端，它現在越來越像一個被磨平稜角的產品經理，回覆四平八穩，但在處理複雜的異步 CI 流程優化時，那種過度的安全護欄反而成了阻礙。Gemini 則依舊在大上下文的汪洋大海裡沉浮，雖然能吞下整個代碼庫，但在精確執行單一重構指令的成功率上，始終差了那麼一口氣。

我們正處於一個很詭異的轉折點。一方面，我們希望模型能像人類一樣思考，所以我們誘導它寫 Reasoning；另一方面，當我們真正要解決 CI 部署變慢、數據遷移報錯這種硬核問題時，我們又恨不得它閉嘴，趕快把代碼吐出來。在與 DeepSeek 等同類產品的市場聲量競逐中，四大平台顯然都在調整自己的輸出策略。是該把運算資源分配給那種花俏的、給外行看的「思維鏈展示」，還是該把權重留給那些真正能跑通的生產環境腳本？這不只是技術問題，這關乎這些 AI 公司到底想服務哪種人。

目前的技術共識正向「沉默的強大」傾斜。如果你還在 Prompt 裡寫「請解釋你為什麼選擇這個方法，不少於三句話」，那你可能還沒玩明白這一代模型的脾氣。Opus 的強大在於它能識別你的具體約束——比如你更在乎 CI 跑完的總時長還是雲端帳單上的金額。當你把這些硬性指標丟給它，它能給出一個幾乎不需要修改的執行計劃。這種從「對話」到「執行」的轉型，才是這波技術迭代最核心的推動力。

但這裡有個問題始終沒人能給出標準答案：如果我們不再要求 AI 展現推理過程，我們該如何預判它何時會產生那種足以致命的、邏輯自洽的幻覺？當模型在長達一小時的任務中保持沉默並持續輸出代碼，這種「信任」到底是基於它真的變強了，還是我們已經懶得去審核那些我們自己也看不懂的自動化流程了？如果有一天，連開發者都無法分辨模型是在優化代碼還是在埋下隱患，那這種高效的產出，究竟是在幫我們解決問題，還是在加速技術債的崩塌？
