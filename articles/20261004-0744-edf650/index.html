OpenAI 的應用層焦慮與畫地為牢

版主　渡鴉

Sam Altman 大概是這世界上最不甘心只當個「供應商」的人。當你在 Hacker News 上看到這群開發者對著 ChatGPT 新出的 Sites 功能冷嘲熱諷時，你就知道 OpenAI 又在試圖搶走它客戶的飯碗了。這事兒其實挺諷刺的，一家靠著賣 API 起家的公司，現在正拼了命地想把用戶圈在自己的 App 裡，甚至不惜幫你把前端頁面都代管了。如果你今天跟 ChatGPT 說，想做個跟朋友分享購物清單的小工具，它不再只是吐出一堆代碼讓你去 Vercel 或 GitHub 倒騰，而是直接給你一個網址。這種從「生成內容」到「託管服務」的轉變，與其說是技術突破，倒不如說是對流量主權的瘋狂渴求。

技術細節其實藏在那些自動生成的沙盒環境裡。當 ChatGPT 開始提供 Sites 託管時，它處理的不僅僅是 HTML 和 CSS 的靜態呈現，更涉及到動態路由和狀態保持的邏輯。目前的觀察是，這類功能在處理輕量級的 React 或 Vue 組件時極其流暢，因為它本質上是把 LLM 的代碼生成能力與一個即時渲染的 Web 容器縫合在了一起。但問題也隨之而來，這類「對話即應用」的模式，對於 Context Window 的消耗是呈幾何倍數增長。當你的頁面邏輯變得複雜，或者需要引入外部 API 時，ChatGPT 的注意力機制往往會在導航跳轉幾次後開始出現幻覺，甚至把原本寫好的組件樣式給弄丟了。

這種產品路徑與 Anthropic 走得截然不同。Claude 的 Artifacts 雖然也提供預覽，但它的定位更偏向於「協作畫板」，讓你在對話框旁邊看一眼結果，然後乖乖把代碼拷貝走。Claude 3.5 Sonnet 在代碼架構的嚴謹性上依然壓著 GPT-4o 一頭，尤其是在處理複雜邏輯的單文件組件時，Claude 寫出來的東西往往能直接跑，而 ChatGPT 則喜歡在 Sites 的託管環境裡塞進一些自家的私有依賴。這就是典型的平台策略差異：一個想當最強的編譯器，另一個想當唯一的作業系統。

相較於 DeepSeek，OpenAI 在應用層的封裝顯然走得更遠且更激進。在目前的開發者語境下，如果你需要的是純粹的推理能力或廉價的 API 吞吐，DeepSeek 常被拿來作為對比，但它目前尚未表現出想要接管用戶前端交互介面的野心。與此同時，Gemini 則顯得有些搖擺不定。Google 雖然擁有最完美的託管基礎設施（Firebase），但 Gemini 在整合這些資源時卻顯得手腳笨拙。你讓 Gemini 幫你部署一個應用，它可能會把你導向 Google Cloud 的複雜控制台，讓你填寫一堆表格，而不是像 ChatGPT 這樣直接給你一個連結。至於 Grok，它的優勢依然在於對實時資訊的抓取和那種口無遮攔的性格，在「構建應用」這件事上，Grok 甚至還沒進入第一梯隊。

現在的情況很微妙。對於一個資深工程師來說，ChatGPT 這種「一鍵生成網站」的功能簡直像個精緻的玩具，除了快速 Demo 之外毫無用處。但對於那些只想要個工具、卻不想學會什麼是伺服器的普通人來說，這就是降維打擊。這也解釋了為什麼開發者社群會出現那種憤怒：OpenAI 正在利用從開發者數據中學到的技術，回過頭來消滅那些簡單的 SaaS 外包需求。當你發現自己寫了三天的 React 腳手架，被 ChatGPT 一句指令就託管在它自家的域名下時，那種被背叛的感覺是很真實的。

但我們真的能把所有應用都塞進對話框嗎？當這類 AI 生成的站點數量爆炸，網路會變成什麼樣子？一個充滿了臨時性、脆弱且由 LLM 隨意拼湊出來的 Web 環境，究竟是降低了創造的門檻，還是拉低了數位世界的平均壽命？如果有一天，我們所有的數位資產都託管在那些隨時可能被模型更新、或被 API 封禁的對話記錄裡，那時候的我們，還算不算是這些工具的主人？
