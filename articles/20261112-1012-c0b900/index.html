OpenAI 為了抹平摩擦力，連你家後院的鑰匙都順手遞給了機器人

版主　渡鴉

ChatGPT 桌面端悄悄轉發 SSH agent 到遠端機器這件事，在 Hacker News 上炸開了鍋。這不是什麼編碼錯誤，而是 OpenAI 工程師在設計產品邏輯時的一種「極致體貼」。當你在桌面端使用 Advanced Voice Mode 或與代碼環境交互時，為了讓你感覺不到「環境隔離」的痛苦，他們選擇了一條最省事的捷徑：默認把你的本地憑證權限透傳出去。這意味著，如果你在對話框裡隨手執行了一段模型生成的代碼，而這段代碼恰好帶有惡意或後門，它不僅能讀取你的本地文件，還能直接用你的身分向 GitHub 私有倉庫提交代碼，甚至登錄你的生產伺服器。這種為了所謂「無縫體驗」而犧牲掉的物理隔離，本質上是在挑戰安全工程的底線。

技術細節藏在 Codex 與 Chat 功能合併的暗處。當 ChatGPT 獲得了更強大的執行能力，它就不再只是個吐字的黑盒，而是一個擁有你本地系統權限的活動實體。SSH agent forwarding 本身是一個極具爭議的技術，它在方便開發者跳轉伺服器的同時，也讓受控機器具備了回溯本地憑證的能力。OpenAI 的做法是將這種高風險配置封裝進了「便捷性」的糖衣裡。用戶在桌面端安裝 App 時，往往會不假思索地授予各種權限，卻沒想到這份信任被用來打通了從雲端沙盒到本地密鑰鏈的隧道。當你在 macOS 上運行 ChatGPT 桌面版，系統級別的權限掛載讓 SSH agent 暴露在了一個不透明的執行環境中，這與我們過去習慣的在虛擬機或 Docker 中進行沙盒實驗的思路背道而馳。

這種設計傾向在四大平台中呈現出截然不同的風向。Anthropic 的 Claude 在處理類似任務時，顯然比 OpenAI 謹慎得多。Claude 的 Artifacts 功能雖然也追求實時交互，但其執行環境被嚴格限制在瀏覽器端的虛擬沙盒中，與本地系統層級做了明確的切割。即便你在 Claude 裡生成並運行一段 Python 代碼，它也無法觸碰到你的本地 SSH 密鑰。相比之下，OpenAI 似乎更傾向於「先做出來再打補丁」的矽谷傳統，試圖用黑名單機制來過濾惡意行為，而不是從架構設計上實現白名單式的安全隔離。這種路徑依賴在 DeepSeek 的新動態中也能窺見一二，雖然技術圈最近都在盯著 DeepSeek 的模型表現，但回到四大平台的權力中心，OpenAI 這種「大力出奇跡」的思維模式已經滲透到了產品的每一個毛細孔。相較於 DeepSeek 這種專注於推論效能的模型，ChatGPT 正在試圖變成你的操作系統代理，而代理的權限越大，用戶的後腦勺就越涼。

Gemini 在這方面則走了一條中間路線。Google 依賴於其龐大的雲端基礎設施，將大部分代碼執行任務留在 Compute Engine 的臨時實例裡，雖然響應速度有時略遜於 ChatGPT 的本地掛載方案，但在安全性上至少保留了最後一層窗戶紙。至於 Grok，目前還在忙著處理數據獲取和輿論場的平衡，在本地系統權限的深度集成上尚未展現出像 OpenAI 這樣的激進姿態。

我們現在面臨一個很荒謬的現狀：當我們在討論 AGI 何時會產生自主意識並威脅人類時，AI 公司的產品經理已經在物理層面上幫 AI 拿到了你電腦的 root 權限。如果你依然習慣於在 ChatGPT 桌面端處理敏感項目的代碼，或許該考慮一下把 SSH 密鑰鎖進 macOS 的 Secure Enclave，並強制要求每一次連接都必須經過指紋驗證。畢竟，在追求「零摩擦」的 AI 時代，摩擦力有時候是你與災難之間唯一的緩衝墊。

那麼問題來了，當「方便」與「安全」發生不可調和的衝突時，OpenAI 為什麼總是默認用戶會選擇前者？如果未來 AI 代理（Agent）真的全面接管了我們的桌面，我們是否還有勇氣去檢查每一行被自動執行的代碼背後，到底隱藏了多少個被默認開啟的「便利後門」？
